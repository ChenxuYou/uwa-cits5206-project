## 3. Marking rubric

**Total: 15 points.** Each criterion has three levels: *Novice*, *Competent* and *Proficient*.
Three of the four card headings carry a note in brackets on what the criterion is marked from;
it is kept in each heading below.

| # | Criterion | Marked from | Points | Weight |
| --- | --- | --- | --- | --- |
| 3.1 | Delivered Project | The submitted report and the repositories it links to | 3 | 20% |
| 3.2 | Deployment and Documentation | The README and other guides in the repository; the marker runs the project from the README | 4 | 26.67% |
| 3.3 | Responsible use of AI | Not stated on the card | 3 | 20% |
| 3.4 | Client Feedback | The client, whom the unit coordinator may contact after submission | 5 | 33.33% |
| | **Total** | | **15** | **100%** |

### 3.1 Delivered Project (Docs: submitted report with links to repositories)

**3 possible points (20%)**

| Level | Points | Description |
| --- | --- | --- |
| Novice | 0 – 1 | Insufficient evidence of project deliverables, quality assurance and limitations in the submitted report and/or project repository. |
| Competent | 1.5 – 2 | Only some of the planned MVP was delivered. Report is over-length or lacks informative summary of the project, its deliverables, quality assurance and limitations (future work). |
| Proficient | 2.5 – 3 | Report provides a concise and informative summary of the project, its deliverables, quality assurance and limitations (future work). Code base is well organised. Remaining open issues (bugs/features) are documented in the project repository. Project delivers the planned MVP (and maybe more!). |

### 3.2 Deployment and Documentation (Docs: Readme and any other guide documents in Project Repository eg github. The marker will attempt to run your project using your Readme instructions)

**4 possible points (26.67%)**

| Level | Points | Description |
| --- | --- | --- |
| Novice | 0 – 1 | Demo does not run. Insufficient user guidance. Project is not ready for handover to the client. Project fails to deliver the planned MVP. |
| Competent | 1.5 – 2.5 | Project runs but with some errors or Little evidence of client acceptance testing or Ongoing issues have not been recorded. |
| Proficient | 3 – 4 | Submitted code runs smoothly for demonstration; The deployment instructions, user manual (and any other training material) is well laid out, accessible, clear and succinct. New users are able to learn the system effectively with the provided documentation. |

### 3.3 Responsible use of AI

**3 possible points (20%)**

| Level | Points | Description |
| --- | --- | --- |
| Novice | 0 – 1 | AI use, where applicable, is not clearly acknowledged or explained, and there is little evidence of critical judgement or appropriate use. |
| Competent | 1.5 – 2 | AI use is acknowledged and generally appropriate, but the explanation of how AI was used, evaluated, or adapted is limited. |
| Proficient | 2.5 – 3 | AI use is clearly and transparently acknowledged where applicable, with appropriate use and clear evidence that AI-generated outputs were critically evaluated, adapted, and integrated into the work. |

### 3.4 Client Feedback (The unit coordinator may contact the client after project submission)

**5 possible points (33.33%)**

| Level | Points | Description |
| --- | --- | --- |
| Novice | 0 – 1.5 | Client has some serious reservations about the delivered project. |
| Competent | 2 – 3.5 | Client is satisfied with the project and project handover. |
| Proficient | 4 – 5 | Client is delighted with the delivered project and project handover. |

**Transcription notes.** The wording and point ranges above are exactly as on the cards,
including a few oddities that are the cards', not typos of ours: in 3.2 *Competent*, "Little"
and "Ongoing" are capitalised mid-sentence; in 3.2 *Proficient*, a semicolon is followed by a
capital ("; The deployment"), and "is well laid out" follows a plural subject; and 3.3 is the
only card with no note in brackets on what it is marked from.

## 4. Reading the brief and rubric

Our reading, not the unit's words.

| # | What the brief and rubric say | What it means in practice |
| --- | --- | --- |
| **R1** | **A third of the mark is not in the PDF.** *Client Feedback* is 5 of the 15 points, and the unit coordinator may ask the client directly. Both upper bands are about the project **and the handover** | The handover (M7 in [`plan.md`](../../docs/project/plan.md)) has to have happened, and gone well, by the time the coordinator asks — not be promised in the report. Confirm with the client that they have what they need to run and rehost the tool, and that the right contact is on record in [`docs/client/contacts.md`](../../docs/client/contacts.md) |
| **R2** | **The marker will run it from the README.** *Deployment and Documentation* is the largest criterion the team still controls (4 points), and its *Novice* band opens with "Demo does not run" | Before submission, someone who did not write the setup steps follows them from a fresh clone on a clean machine, exactly as written. The root [`README.md`](../../README.md) should send a newcomer straight to [`src/README.md`](../../src/README.md) to run it and [`deploy/README.md`](../../deploy/README.md) to deploy it |
| **R3** | **A user manual is asked for, not only setup steps.** *Proficient* names "the deployment instructions, user manual (and any other training material)", so that "new users are able to learn the system" | The repository's guides are written for developers and operators; as of 7 October there is no guide for the people who will use the tool. One is needed — short, task-based, with screenshots — linked from the README and from the report |
| **R4** | **Open issues must be recorded in the repository.** *Proficient* for 3.1 asks that "remaining open issues (bugs/features) are documented in the project repository"; for 3.2, "Ongoing issues have not been recorded" is enough on its own to cap the criterion at *Competent* | Every known bug, gap and unbuilt feature is a GitHub issue, labelled, and the report links the filtered list. The *Known gaps* section of [`src/README.md`](../../src/README.md#known-gaps) should agree with those issues, not stand in for them |
| **R5** | **Client acceptance testing needs evidence.** "Little evidence of client acceptance testing" is likewise enough to cap 3.2 at *Competent* | A dated session in which the client works through the MVP stories on the deployed build, minuted in [`docs/meetings/client/`](../../docs/meetings/client/) and linked from the report. A demo the team drives is weaker evidence than the client using the tool themselves |
| **R6** | **Responsible use of AI is new, and wants more than a disclaimer.** No earlier rubric in this unit had it. Acknowledgement alone is *Competent*; *Proficient* needs "clear evidence that AI-generated outputs were critically evaluated, adapted, and integrated" | A section saying which tools were used and for what, with concrete examples of output that was checked, corrected or rejected, and how — code review, tests, the client's worked example. The commit history does not show this by itself, so the report has to |
| **R7** | **Five pages, concise, summary-level.** "Over-length" alone is named in *Competent* for 3.1 | Each section summarises and links; the detail stays in the repository. The 5 pages are the whole report, cover and contents included (O4) |
| **R8** | **The suggested structure maps onto the rubric, except for AI.** Requirements and solution, verification and tests, and discussion and future work cover 3.1; user guides and deployment cover 3.2 | Use the suggested headings and add one for AI use (3.3). Assignment 1 lost a point for having no cover page or table of contents ([feedback F4](../../docs/assignments/assignment-1/feedback.md#5-what-changes-and-where-it-is-written-down)), and the brief now lists the table of contents first |
| **R9** | **"As with earlier deliverables, include links"** | The Assignment 1 lessons apply in full: full visible `https://…` URLs, none wrapping mid-path, each opened signed out from the built PDF (F1–F3 in the same file). Pin file links to the tagged final release, as the D2 report pinned them to a commit, so the marker sees what was submitted |
| **R10** | **The peer evaluation weights the group mark** | Every member completes the Group Member Evaluation on Feedback Fruits before Monday of week 13, 23:59. It is individual and separate from the report, and the one submitter cannot do it for the others |
